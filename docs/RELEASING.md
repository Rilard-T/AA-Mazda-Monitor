# Ключ подписи и выпуск релизов

Документ для владельца репозитория. Кода не касается, но без него релизы не собрать.

## 1. Ключ подписи — самое ценное в проекте

Обновление ставится поверх старой версии только при совпадении сертификата.
Сейчас подпись: `CN=Echo`, SHA-256 `EA:0E:40:B9:72:BF:C4:B4:5E:32:D9:72:E8:AE:91:DC:23:B6:9A:AC:29:A8:C6:86:3D:BE:7C:49:4E:77:94:8`.

Если ключ или пароль потерян, пользователи не смогут обновиться: придётся удалять
приложение (и журнал прожигов, и настройки) и ставить заново через AAEnabler.
Поэтому:

1. Храните `.jks` (в CI это `KEYSTORE_B64`) минимум в двух независимых местах:
   менеджер паролей с вложениями (Bitwarden/1Password/KeePassXC) и офлайн-копия
   (зашифрованный архив на флешке или диске, который лежит не рядом с ноутбуком).
2. Пароли `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` — в менеджере паролей,
   отдельной защищённой записью со ссылкой на файл ключа.
3. Раз в год проверяйте восстановление: развернуть копию во временную папку и
   выполнить `apksigner verify --print-certs` на любом старом APK — отпечаток
   должен совпасть с указанным выше.
4. Не перевыпускайте ключ «на всякий случай»: новая подпись = обязательное удаление
   приложения у всех пользователей.

## 2. Где что лежит

| Что | Где |
|---|---|
| Ключ в base64 | секрет репозитория `KEYSTORE_B64` (Settings → Secrets and variables → Actions) |
| Пароли | там же: `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` |
| Сборка и публикация | `.github/workflows/release.yml`, запуск вручную: Actions → release → Run workflow |
| Проверка PR | `.github/workflows/ci.yml`: юнит-тесты и `assembleDebug` на каждый pull request |

## 3. Выпуск версии

1. Поднять `patchVersion` в `version.properties` (код версии считается как
   `major * 100000 + minor * 1000 + patch`).
2. Обновить `README.md` и `README.en.md`, если менялись возможности.
3. Смержить PR в `master`.
4. Actions → **release** → **Run workflow**, ветка **master**. Тег создаётся из
   `version.properties` и ставится на коммит сборки (`--target "$GITHUB_SHA"`).
5. Проверить на странице релиза: тег, APK (~15,8 МБ), `mapping.txt` (нужен для
   расшифровки стектрейсов из журнала) и архивы исходников.
6. Проверить на телефоне: установка поверх предыдущей версии, список PID,
   «Проверить обновления».

Релиз на уже существующем теге падает: `gh release create` не перезаписывает теги.
Нужен перевыпуск — удалить релиз и тег в UI, затем запустить workflow снова.

## 4. Обфускация и журналы

В release включён R8, поэтому имена классов и методов в стектрейсах сокращены.
Файл `app/build/outputs/mapping/release/mapping.txt` прикладывается к каждому релизу:
сохраняйте его вместе с APK, иначе разбирать жалобы на падения будет нечем.

## 5. Почему код приложения не обфусцируется

В `app/proguard-rules.pro` есть строка `-keep,allowoptimization class com.aatorque.** { *; }`.
Это намеренное решение, а не наследие: журнал (`Файл .txt` в отчёте об ошибке) разбирается по
тегам, а Timber берёт тег из имени класса. Без этого правила в релизе вместо `ObdEngine`,
`RegenTracker`, `TorqueRefresher` появились бы `a`, `b`, `c`, и диагностика по журналу умерла бы.

Библиотеки при этом обфусцируются: 0.8.3 (без обфускации) — 21,6 МБ, 0.8.4 (с обфускацией
библиотек) — 16,6 МБ; разница не только от неё, но вклад заметный. Если где-то код обращается к библиотеке по имени, это место надо
привязать к типу (как `CardRecyclerView.addItemDecoration`) или закрыть точечным `-keep`,
а не снимать правило для всего приложения.
