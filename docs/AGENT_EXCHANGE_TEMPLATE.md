# Шаблон обмена `master` ↔ `nav`

Файл: `docs/MASTER_TO_NAV.md` или `docs/NAV_TO_MASTER.md` (один файл на направление).
Обновляется **только при значимых изменениях** (новый функционал, блокер, вопрос к другой ветке).
Формат — Markdown с фиксированными заголовками, чтобы агент мог быстро найти нужный раздел.

---

```markdown
# Отчёт {источник} → {получатель}

<!-- МЕТАДАННЫЕ: агент читает первую строку после заголовка -->
- **Ветка:** `{ветка}` = `{короткий хэш коммита}`
- **Дата:** YYYY-MM-DD
- **Версия:** X.Y.Z (из version.properties, не менять без команды)
- **Состояние:** ✅ актуально / ⚠️ есть блокер / ❓ ждёт ответа

## 1. Что сделано
<!-- Маркированный список: каждый пункт — одна строка, начинается с глагола -->
- **{Компонент}:** {что изменилось} (`файл.kt`, `+N/-M`)
- ...

## 2. Что НЕ менялось (явно)
<!-- Чтобы другая ветка не искала несуществующие изменения -->
- `version.properties`, `applicationId`, формула `versionCode`
- ...

## 3. Изменения, затрагивающие общее ядро
<!-- OBD-код, общие UI, build.gradle — то, что нужно перенести в обе ветки -->
| Файл | Изменение | Нужно в nav? |
|---|---|---|
| `app/src/.../Foo.kt` | описание | да/нет |

## 4. Открытые вопросы к {получатель}
<!-- Нумерованный список, каждый вопрос — отдельный пункт -->
1. {Вопрос}? — {варианты ответа}
2. ...

## 5. Блокеры
<!-- Если нет блокеров — написать "Нет" -->
- {Описание блокера}: {что нужно для разблокировки}

## 6. Что проверено
| Проверка | Итог |
|---|---|
| `:app:testStableDebugUnitTest` | ✅ BUILD SUCCESSFUL, N тестов |
| `:app:assembleStableDebug` | ✅ BUILD SUCCESSFUL |

## 7. Рекомендации по координации
<!-- Опционально: что делать другой ветке с этой информацией -->
- {Рекомендация}
```

---

## Правила использования

1. **Один файл на направление.** `MASTER_TO_NAV.md` пишет master-агент, `NAV_TO_MASTER.md` — nav-агент. Не перезаписывать чужой файл.
2. **Не удалять историю.** Если файл устарел — добавить пометку «Устарело, см. коммит X» в начале, а не удалять. Nav-агент уже делал так (старая версия оставалась в git-истории).
3. **Коротко.** Агент читает файл целиком — не писать простыни. Детали — в коммитах и коде.
4. **Ссылки на коммиты.** Каждое изменение привязывать к хэшу коммита, чтобы nav-агент мог сделать `git show` или cherry-pick.
5. **Общее ядро — отдельно.** Раздел 3 обязателен, если затронуты файлы из `app/src/main/java/com/aadash/obd/` или общие UI-компоненты. Nav-агент должен знать, что переносить.
6. **Блокеры — честно.** Если пуш заблокирован, сборка не проходит, или нужен токен — указать в разделе 5, а не прятать.
7. **Не дублировать README.** Файл обмена — про изменения и координацию, а не про описание проекта.
8. **Обновление, а не перезапись.** При добавлении нового пункта — append в нужный раздел, а не переписывание всего файла. Это сохраняет историю решений.

## Как агенту быстро найти нужное

```bash
# Прочитать файл обмена
cat docs/NAV_TO_MASTER.md

# Найти только блокеры
grep -A3 "## 5. Блокеры" docs/NAV_TO_MASTER.md

# Найти изменения общего ядра
grep -A10 "## 3. Изменения, затрагивающие общее ядро" docs/NAV_TO_MASTER.md

# Посмотреть, какие коммиты упомянуты
grep -oE "[0-9a-f]{7,}" docs/NAV_TO_MASTER.md | sort -u
```
